‘**concurrent**’ = ‘at the same time as others’. Мы пишем concurrent код в надежде, что он будет выполняться параллельно.

закон Мура: количество компонентов на чипах удваивается каждый год (1965-1975). Затем — каждые 2 года. В ~2012 сломался. Вектор вычислений сменился на параллельные (выжимаем мощность из кода, а не из чипов).

Появились облачные мощности. Сейчас важно, что код таков, что добавить 10 подов в кубернетес (web scale).

Писать параллельные приложения очень трудно, в них постоянно возникают баги. Иногда они могут всплыть спустя пару лет при изменении условий среды.

Но Go с этим очень помогает. В нём есть горутины и каналы — новый уровень абстракции от потоков в ОС. Если на плюсах нужно запускать thread pool и возиться с ним, то в Go мы просто запускаем новую горутину (скажем, для нового соединения у веб-сервера). Go’s runtime сам управляет распределением горутин по потокам. Если у нас 6 горутин и всего 2 ядра, то для каждого ядра он попеременно запускает ~3 горутины. Если одна из них заблочилась (например, каналом, ждущим вызов), то она помещается в очередь и на поток становится другая. При помощи select’а можно ждать несколько событий одновременно и реагировать на первое пришедшее.

Философия Go такова: лучше использовать каналы, а не mutex’ы, когда возможно.

1. Если изменяется владелец данных (функция producer сделала что-то и передала в consumer), то лучше использовать каналы.
2. Если нужно обработать несколько сценариев, тоже используем каналы:

   ```go
   select {
   case job := <- jobs:
   	handle(job)
   case <- ctx.Done()
   	return
   case <- time.After(5 * time.Second):
   	log.Println("idle")
   }
   ```

3. Если нам нужно защищать _**внутреннее**_ состояние структурки, то нужно использовать mutex. Важно следить за тем, чтобы это скрывалось.

   ```go
   type Counter struct {
   	val int
   	mu sync.Mutex
   }
   func (c *Counter) Inc() {
   	mu.Lock()
   	val++
   	mu.Unlock()
   }
   ```

4. Если очень-очень важна производительность, то можно заменить каналы на mutex’ы (т.к. каналы внутри используют mutex’ы и, достав лишь необходимое из их внутренностей и убрав лишние, мы ускорим код).

# Почему параллельные вычисления такие сложные?

## Race conditions

**Race condition (состояние гонки)** — когда результат работы программы не определён:

Одна программа — 3 возможных исхода в зависимости от того, кто кого обгонит, какая горутина исполнится первой.

```go
var data int
go func() {
	data++ // 1
}()
// time.Sleep(time.Second * 1) // bad!
if data == 0 { // 2
	fmt.Println("the value is %v\n", data) // 3
}
```

Исход 1: сначала произошло увеличение, а только потом проверка if ⇒ ничего не вывелось

Исход 2: сначала произошла проверка if, а только потом увеличение ⇒ вывелся 0

Исход 3: сначала произошла проверка if, а затем — увеличение ⇒ вывелся 1

Писать Time.sleep() не выход! Программа всё так же будет иметь 3 исхода. Просто изменится распределение вероятностей в пользу одного из сценариев. Следует писать крутой код.

## Atomics

Каждая операция может быть **атомарна** в своём контексте. `i++`, вроде бы, атомарна, но разбивается на 3 части (прочитать в регистр, увеличить, положить обратно).

Можно защитить **критические секции** — части программы, которые обращаются к одному и тому же ресурсу, при помощи **mutex**’ов (mutual exclusion — взаимосключение):

!go_concurrency-5.svg

Таким образом, исключим 3-й случай, но состояние гонки всё ещё сохранится.

Помимо того, мы замедлили программку и ввели нежелательный паттерн кода.

## Deadlocks

**Deadlock** — когда один процесс заблокировал часть процессов и хочет заблокировать вторую, а её уже заблокировал другой. В итоге они оба ждут друг друга:

!go_concurrency-6.svg

Есть официальные критерии (Coffman Conditions) для их обнаружения, но проверять каждый из них в реальном коде трудно.

## Livelocks

**Livelock** — когда процессы понимают, что блокируют друг друга и пытаются сами исправить эту ситуацию, но у них не получается (из-за отсутствия координации). Похоже на случай, когда люди в коридоре пытаются друг друга пропустить и делают шаги влево и вправо одновременно.

!go_concurrency-10.svg

## Starvations

**Starvation** — ситуация, когда процесс не может получить все ресурсы, которые необходимы ему для работы. У него есть a.Locked, но нету b.

Чаще всего случается так: есть жадный процесс, который надолго блокирует ресурс, из-за чего другие “голодают” и вынуждены ждать.

```go
greedyWorker := func() {
	defer wg.Done()

	var count int
	for begin := time.Now(); time.Since(begin) <= runtime; {
		sharedLock.Lock()
		time.Sleep(3 * time.Nanosecond)
		sharedLock.Unlock()
		count++
	}

	fmt.Printf("Greedy worker was able to execute %v work loops\n", count)
```

```go
politeWorker := func() {
	defer wg.Done()

	var count int
	for begin := time.Now(); time.Since(begin) <= runtime; {
		sharedLock.Lock()
		time.Sleep(1 * time.Nanosecond)
		sharedLock.Unlock()

		sharedLock.Lock()
		time.Sleep(1 * time.Nanosecond)
		sharedLock.Unlock()

		sharedLock.Lock()
		time.Sleep(1 * time.Nanosecond)
		sharedLock.Unlock()

		count++
	}

	fmt.Printf("Polite worker was able to execute %v work loops\n", count)
```

## Написанный другими людьми код

Вот есть сигнатура функции:

```go
func CalculatePi(begin, end int64, pi *Pi)
```

- Нам надо запускать несколько горутин из неё?
- Каждый запуск пишет в *Pi, нужно ли ставить mutex? Или внутри Pi он уже есть?

Поэтому можно или написать комменты (эта функция сама внутри запускает горутины, работающие со структурой Pi, которая внутри сама себя защищает), или делать более понятные сигнатуры:

```go
func CalculatePi(begin, end int64) []uint
```

- нет *Pi, не нужно думать о mutex’ах

```go
func CalculatePi(begin, end int64) <-chan uint
```

- нам вернётся канал, из которого можно только читать (значит, в него потихоньку будут записываться значения)
