Каждая программа имеет как минимум одну — `main()`.

**Горутина** — функция, которую попросили начать выполняться параллельно при помощи слова `go`:

```go
func main() {
	go sayHello()
	// continue doing other things
}

func sayHello() {
	fmt.Println("hello")
}
```

На самом деле, это частный случай корутины — функции, которую разработчик не может остановить, когда ему захочется. Её паузами занимается рантайм Go. Когда она чего-то ожидает, рантайм останавливает её и запускает другую.

Модель их распространения выглядит так: одна горутина порождает дочернюю, которая выполняется параллельно. Но должна быть точка их соединения воедино:

!go_concurrency-11.svg

…, которой в нашем примере не было. Поэтому “hello”, вероятнее всего (так и есть на практике), вообще не выведется.

Происходит race condition: а что случится первее — main закончится или запустится горутина?

Можно было бы использовать time.Sleep(), но это плохой вариант. Вот правильное исправление:

```go
var wg sync.WaitGroup
wg.Go(func() {
	fmt.Println("hello")
})
wg.Wait()
```

> wg.Go() увеличивает счётчик на 1, добавив 1 горутину в wait-группу. Он уменьшится, когда случится скрытое внутреннее wg.Done(). Как только он достигнет нуля, wg.Wait() перестанет блокировать.

# Особенности поведения горутин и внешних переменных

Если вызываем горутину внутри функции main, то получаем замыкание. При нём изменится **оригинал** переменной:

```go
salutation := "hello"
go func() {
	salutation := "welcome"
}()
wg.Wait()
fmt.Println(salutation) // "welcome", not "hello"
```

Общая форма — `go func() { … x … }()` или `wg.Go(func() { … x … })`. Значения переменных вычисляются **в момент реального исполнения** горутины!

```go
x := 1
wg.Go(func() {
	fmt.Println(x) // 1 OR 2!
})
x := 2
```

Противоположный случай — переменная, переданная аргументом — `go func(x)`. Во-первых, она **копируется** (т.е. оригинал изменить никак нельзя). А во-вторых, значение определяется **в момент объявления** горутины:

```go
x := 1
go fmt.Println(x) // ONLY 1
x := 2
```

Раньше (Go 1.21-) поведение замыканий плохо сочеталось с циклами. Итерационная переменная была одна. Поэтому она быстро добегала до финального значения, а горутины пытались что-то сделать с ним:

```go
for _, salutation := range []string{"hello", "greetings", "good day"} {
	wg.Go(func() {
		fmt.Println(salutation) // "good day", "good day", "good day"
	})
}
```

С Go 1.22+ каждая переменная (i, salutation, …) копируется для тела.

# Ресурсы, занимаемые горутинами

Горутины ооочень лёгкие. У автора книжки вышло 2.8КБ на одну, у меня — 3.056КБ. Значит, 6GB памяти ~ 6 000 МБ памяти ~ 6 000 000 КБ памяти ~ 2 миллиона потенциальных горутин.

- Код для измерения (advanced)

  ```go
  memConsumed := func() uint64 {
  	runtime.GC()
  	var s runtime.MemStats
  	runtime.ReadMemStats(&s)
  	return s.Sys
  }
  var c <-chan interface{}
  var wg sync.WaitGroup
  noop := func() { wg.Done(); <-c }
  const numGoroutines = 1e4
  wg.Add(numGoroutines)
  before := memConsumed()
  for i := numGoroutines; i > 0; i-- {
  	go noop()
  }
  wg.Wait()
  after := memConsumed()
  fmt.Printf("%.3fkb", float64(after-before)/numGoroutines/1000)
  ```

Там используется тот факт, что горутины не чистятся сборщиком мусора: если она каким-то образом навсегда зависла, то она так и будет висеть, пока не завершится процесс программы.

Минимальный стек на каждую горутину — ровно 2 КБ. Его можно увеличить, если мы знаем, что работаем с какими-то тяжёлыми объектами (чтобы он каждый раз сразу выделялся на нужный размер, а не растягивался с 2 КБ).

Помимо веса, у них также быстро работает смена контекста — когда запоминается и откладывается внутреннее состояние функции, чтобы начала выполняться другая. Она работает в 6-7 раз быстрее (на 92%, говорит книжка), чем у потоков ОС.

# Результат работы горутин

Сами горутины ничего не возвращают. Для того, чтобы как-то посмотреть на результат их работы, нужно либо использовать каналы, либо общую память под mutex’ом.

# Потоки и горутины

Одно ядро процессора соответствует одному потоку. Параметр `GOMAXPROCS=2`, говорит о том, что, если у системы есть ресурсы, то наш код будет выполняться на двух потоках.

Это означает, что по-настоящему одновременно в нём смогут выполняться ровно 2 горутины.

Если мы запустим какое-то большее число, например, 6 штук, то scheduler будет на одном потоке выполнять сначала одну из трёх горутин, затем — вторую, после — снова первую и т.д.

# Паника в горутине

Если паника случится в ответвлённой горутине, то recover() её не поймает!

```go
func main() {
	var wg sync.WaitGroup
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("caught:", r)
		}
	}()

	wg.Go(func() {
		panic("boom")
	})
	wg.Wait()

	fmt.Println("main done")
}
```
